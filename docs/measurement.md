# 計測の仕様

## 用語

| 用語 | 意味 |
| --- | --- |
| 操作 | サーバーへの頼みごとの種類。作成・一覧・1件取得・更新の4つ |
| 準備運動 | 本番の前に、同じリクエストを 5秒送り続けること。Node.js は動かし始めが遅く、同じ処理をくり返すうちに速くなるので、この間の結果は捨てる |
| 同時 50本 | 返事が来たらすぐ次を送る、を 50本並べて続ける |

## コマンド

| コマンド | 対象 | 回数 | 保存 |
| --- | --- | --- | --- |
| `npm run bench` | 全フレームワーク | 3回 | `results/日時.json` |
| `npm run bench -- --try 名前...` | 指定したもの | 1回 | しない |

GitHub の Actions タブの `bench` からも実行できる。公開する数字はこちらで測る。手元の Mac の数字は、熱でぶれるので参考程度([ADR 0008](adr/0008-benchmark-location.md))。

## 流れ

1. 全対象に仕様チェックを流す。1つでも不合格なら中止(仕様どおりに動かないものは比べられないため)

2. 「1回の計測」(下記)を、全フレームワーク × 全操作の組み合わせで行う。これを3周する(数字は測るたびにぶれるため)
   - 例: Express と Hono なら、2つ × 4操作 = 8回で1周。3周で24回

3. 組み合わせごとに、3周分の真ん中の値を採用する(例: 5.3万・4.8万・5.1万件/秒 → 5.1万)

## 1回の計測

1つのフレームワークの1つの操作を測る(例: Express の作成)。操作を分けるのは、操作ごとにサーバーの仕事(中身のチェック、100件の返事づくり等)が違い、どこで差がついたか分かるようにするため。約23秒かかる。

1. サーバーを新しく起動する(前の計測で増えたデータやメモリの状態を持ち越さないため)

2. 100件入れる(一覧・1件取得・更新の相手を用意するため)

3. 待機中のメモリを読む(何もしていないときの重さを知るため)

4. 準備運動 5秒(結果は捨てる)

5. 同時 50本で 15秒リクエストを送り、結果を記録する

6. サーバーを捨てる(次の計測と混ざらないため)

## 操作

| 操作 | 送る先 |
| --- | --- |
| 作成 | `POST /tasks` |
| 一覧 | `GET /tasks`(100件) |
| 1件取得 | `GET /tasks/:id`(100件からランダム) |
| 更新 | `PUT /tasks/:id`(100件からランダム) |

削除は計測しない([ADR 0007](adr/0007-no-delete-benchmark.md))。

## データの件数

どの操作も、計測前は 100件。1件は4項目(番号・タイトル・完了かどうか・作成日時)だけの小さなデータ。

| 操作 | 計測中 |
| --- | --- |
| 作成 | 1回ごとに1件増える(20秒で十数万件) |
| 一覧・1件取得・更新 | 100件のまま |

作成だけデータがたまるので、負荷中のメモリの最大値は作成が一番大きく出る。

## 記録する数字

| 数字 | 測り方 |
| --- | --- |
| 1秒あたりの件数 | k6(負荷をかける道具)の集計 |
| 応答の速さ | 平均・50/90/99% の値・最大 |
| 起動時間 | 起動の合図から `GET /tasks` が初めて 200 を返すまで(10ミリ秒おきに確認) |
| 待機中のメモリ | 100件入れた直後 |
| 負荷中のメモリの最大 | 本番の 15秒間、1秒ごとに読んだ最大値 |

計測の条件(マシン・CPU の割り当て・計測開始時に動いていた他の箱)も一緒に保存する。

## 条件

1. サーバーは CPU 1個、k6 は別の CPU 3個に固定([ADR 0005](adr/0005-cpu-allocation.md))

2. k6 も Docker の中で動かし、サーバーと同じネットワークで直接つなぐ([ADR 0004](adr/0004-k6-in-docker.md))
